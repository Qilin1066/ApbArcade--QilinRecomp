# Changelog

All notable changes to this project are recorded here, newest first. Past entries are never rewritten.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html), as in GBTGhoulies-Qilincomp:

- **0.x.y** while the recompiler is being built. A **minor** bump (0.**x**) is a milestone, a **patch** bump (0.x.**y**) a fix.
- **1.0.0** will be the first build that plays the game end to end at original settings.

Each release is a git tag (`vX.Y.Z`). The version is set once, in `project(... VERSION ...)` in `CMakeLists.txt`, and `qilin --version` prints it. Entries before 0.12.0 predate this format and are kept as written.

## [Unreleased]

### Added
- **Wheel input for continuous rotation, and explicit R5/G920 setups.** Continuous wrapping SDL axes are unwrapped per motion event, so turns between game frames are not lost; the axis-period measurement accumulates that same signed travel. The G920 setup uses a 900-degree limited axis with held-at-lock steering. The optional MOZA R5 physical-angle setup reads degrees from the user's Windows x64 MOZA SDK 1.0.1.8 DLL and bypasses a clipped joystick axis; the DLL is not bundled and no Pit House settings or motor motion commands are issued. Errors and angle discontinuities rebase instead of replaying old movement. The page shows the physical-angle connection and actual friction/damping status. See `docs/wheels.md` for setup, SDK requirements and pending hardware verification. Virtual-wheel and arithmetic tests cover seam crossings, multiple complete turns within a frame, reversed input, pause/calibration and reconnection; a Windows test DLL exercises the SDK ABI without proprietary files.
- **Optional gameplay regression tests using local ROMs** (`QILIN_ROM_DIR`, `ctest -L parity`): compare all 6,000 frame-colour hashes of attract mode, a credited game, a seeded random player and self-test between the lifted CPUs and MAME's reference cores on the shared board/video models. The credited game inserts two coins after startup, presses the real siren input and acknowledges the briefing. Missing or truncated output, runner failures and the first different frame fail the test; logs and hashes stay in the build directory. No game data is distributed, and the default tests still need no ROMs.

### Fixed
- **Force feedback was requested without initialising SDL haptics.** Input now owns a matched haptics subsystem reference, releases effects on disconnect, and reports unsupported/failed friction, damping or autocentre requests in the menu. Steering still works without a haptics driver.
- **Paused or reconnected wheel motion could enter the game.** Pausing/resuming and hot-plugging discard pending movement and establish a new position; reports already queued during a pause are not replayed. Stick/mouse fractions and the smoothed keyboard/gamepad pedal are cleared too.
- **The ROM-folder picker shared an ordinary bool and strings across its callback and the main thread.** SDL permits that callback on another thread. Completion now publishes the result through an atomic release/acquire handshake.
- **The primary button did nothing** (gamepad A, Z / Left Ctrl and the first saved button binding). It used Paperboy's IN0 bit 7 (`0x80`), which APB marks unused. It now drives APB's siren/start on bit 3 (`0x08`); fire stays on bit 1 (`0x02`), and X / Space / C remain an alternate siren. The menu and README name the actions. The random player now uses the same corrected mapping. The virtual-controller regression fails on the old mapping; a ROM run confirms the siren starts a credited game and dismisses its briefing.
- **Malformed saved controls could cause invalid memory reads or broken steering.** Bindings now require whole integer indices, valid scancodes and supported axis/hat directions; keyboard reads also check SDL's array bounds. Numeric settings reject non-finite, overflowing and partially parsed values and keep their defaults instead. Regression tests cover damaged settings alongside the existing settings round-trip and virtual-controller tests.

## [0.17.0] - 2026-11-20
The first release with a Windows download that needs nothing installed, and the first with CI green on every platform since 0.15.0 (Windows had failed unseen). Also: the looks, presets and speed options; controllers found in the background; the ROM folder remembered and asked for; one-step build scripts; stick steering with a curve; and cars no longer vanishing in play. The project is now ApbArcade-QilinRecomp.

A soak test after all of the below: 24 random-player games of an hour each (216,000 frames, 24 hours of game time in all) run natively with no stop of any kind (watchdog, unlifted code, crash), and 4 of them identical to MAME's cores on every frame for the whole hour.

- **Controller notices in the window:** each controller found at start-up, connected or disconnected (or found but not openable) is shown for five seconds in the corner, with the settings hint; "No controller found yet" when there's none.
 (with vsync): exact or matched to the display.**
  - *Exact* (the default) keeps the cabinet's 60.1 Hz, and the window now shows the newest finished frame at each refresh (Vulkan's mailbox mode, still tear-free, where the driver offers it).
  - *Match the display* locks the game to a display within 1% of 60 Hz, or of 120, 180 or 240 Hz, where each frame is shown 2 to 4 times (`present_again`). Every frame is shown in turn, with a two-image swapchain so at most one waits; at 60.00 Hz the game runs 0.16% slow. On other rates (50, 75, 144 Hz) and variable-refresh displays the exact speed is kept, which a variable-refresh display shows perfectly anyway.
  - Locked, `apb` checks that the display really paces it. Over two seconds (after the first half second) it must run within 2% of the display's rate; else locking ends and the page says why, so a display that doesn't wait (remote, virtual, a driver ignoring vsync) can't make the game race. Checked on an Xorg dummy display reporting 60.02 Hz with no real refresh: the lock was dropped after a second, and the run went on at 60.1 Hz.
  - The page says what's happening ("Locked to this display's 60.00 Hz: the game runs 0.16% slow").
- **Presets on the Display page**: *Original* (whole multiples, plain pixels: the arcade's picture, and the default), *Arcade monitor* (as big as fits, the CRT look) and *Smooth* (as big as fits, smoothed pixel art). One click sets the picture's size and look (the CRT's sliders back to their defaults); full screen, the display, vsync and the device are left alone. The preset the settings match is highlighted, else "(set by hand)". Checked in `qilin_input_tests`.
- **Looks for the picture** (the settings menu's Display page): plain pixels (a blit, as before), smoothed pixel art, or a CRT. Saved in `apb.ini` (`effect`, `crt_scanlines`, `crt_mask`).
  - *Smoothed pixel art:* an edge-directed upscaler written for this project after the idea of Hyllian's xBR. Where the colours around a pixel's corner say an edge crosses it (at 45 degrees, or shallow or steep at 1:2), the part of the pixel beyond the edge's line takes the neighbour's colour, anti-aliased to one window pixel. Flat areas and straight edges stay exactly as drawn.
  - *CRT:* each raster line is a beam whose height grows with its brightness, with darker gaps between lines, and an aperture grille's phosphor stripes, added up in linear light. APB's monitor stood upright, so the scanlines run down the screen (`Config::upright_tube`). The gaps fade out below about two window pixels a line, where they'd only make moiré. Scanline and stripe strength are sliders.
  - The renderer draws an effect with a fragment shader over the picture's rectangle, in a dynamic-rendering pass the menu shares. The shaders are GLSL in `recomp/runtime/gfx/shaders/`, compiled by `compile.sh` (glslc, checked by spirv-val) to SPIR-V kept beside them, so a build needs no shader compiler. No effect is still a blit.
- **The window's picture without a window** (`Config::output_width`/`output_height`, `read_output()`): `present` also draws what a window that size would show, scaled and through the effect. `qilin_run --look EFFECT:WxH` saves `--frame-out` frames that way. The renderer tests check it plain, smoothed and CRT on llvmpipe with validation.
- **In-between frames, a prototype** (`qilin_tween`, needs ffmpeg): records each band of each frame (scroll, tile banks, video RAM, the resolved motion objects), then draws frames between the game's at in-between scroll and sprite positions, at a raised resolution so fractions of a pixel show. Each sprite is matched to the next frame's (the same sprite within 32 pixels, or one of the same colour and size within 16, as when a car turns), and the text layer and palette come from the nearer frame. It checks itself first: each recorded frame drawn at t = 0 is the reference renderer's, pixel for pixel (601 of 601). In a random game, 1,797 of 1,800 in-between frames could be interpolated and 95% of sprites were matched. It writes a video with the game as it is beside the in-between version.

### Fixed
- **CI's Windows (MSVC) build had failed since 0.15.0**, unseen: three loops over a braced list of plain numbers (in `cfg.cpp`, the pedal test in `input_tests.cpp`, a `cfg` test in `tests.cpp`) took them as `int` and narrowed them to 16 bits, and the reference 6502's `dec_SP`/`inc_SP` passed an `int` as a byte; MSVC warns about both (C4244), and `/WX` makes that an error. GCC, Clang and MinGW don't warn, so local checks passed. The lists now have their 16-bit type and the stack pointer an explicit cast (noted in `m6502_reference.h`'s list of differences from MAME). Clang 19 with `-Wimplicit-int-conversion -Wshorten-64-to-32` finds a superset of these, for checking locally. Then MSVC reached the tests and reported a possible divide by zero (C4723) in the wheel's edge zone, where a test sets the zone's start to 1: the division only runs when it is below 1, and its divisor now has a floor, so the compiler can see that too.
- **Cars, the player's and the traffic, vanished and came back during play** (the owner: "unplayable"). APB uses two motion-object lists a frame, linking object 0 to the top half's list at line ~392 (in vblank) and to the bottom half's at ~194, and each link write asks for the picture to be drawn up to that line first, as MAME's `spriteram_w` does. Our renderer clamped the vblank request to line 383, so it drew the whole of the next frame there and then, with the bottom half's list from the frame before: the line-194 split never happened, and anything only in the top half's list was missing (in a monkey game, the cop car and its aiming reticle for 28 frames running). MAME's screen clips a request outside the visible area to nothing and starts each frame's drawing at line 0; ours now does the same (`Video::draw_through`, and `qilin_tween`'s recorder). Also added MAME's other forced update, which we lacked: atarimo's every 64 lines (`force_update`: drawn through lines 63, 127 ... 319), so each band shows the list and playfield of its time. Found by logging the link writes' lines in real MAME 0.264 (debugger watchpoint) and in ours: the same lines, 194 and 391-394, in both. Gameplay frames now keep a steady count of motion-object pixels where they dropped to none; attract-mode frames compared with real MAME's still match (all but two, where a table drawing in a row at a time meets the beam a fraction of a frame differently, our boot being that much ahead). A unit test draws through a vblank request and checks nothing was drawn and the list at line 0 is the one used; it fails on the old renderer. Lockstep with MAME's cores is unchanged (two monkey games, 6,000 frames each, every frame identical).
- **Steering with a gamepad's stick was far too quick and twitchy** (the owner, on an Xbox controller). The stick was straight (a small push already turned hard) and its full speed was 6 dial counts a frame, over two turns a second of the cabinet's wheel. It now has a response curve, the deflection past the dead zone squared, so half way over turns at 17% of full speed and small pushes make fine corrections; and full speed is 3 counts a frame. Both are sliders on the Controls page (with what they mean in the cabinet's turns a second), saved as `stick_speed` and `stick_curve`; the old `stick_counts` in a saved `apb.ini` is left behind, so everyone gets the new defaults. The arrow keys turn at 60% of full speed, unaffected by the curve. Tested in `qilin_input_tests`: fully over, half way and inside the dead zone.
- **`cfg.cpp` used standard algorithms without `<algorithm>`**: GCC's library includes it anyway; LLVM's libc++ (MinGW, and stricter macOS versions) didn't build it.
- **Three routines nothing reaches weren't lifted** (found by an audit that tried every ROM word outside code and tables as a code entry). The gap pass tested only a gap's first word, so code after data in the same gap was missed: a routine at 9398 and two `JMP @#f` stubs at 998A and 998E. Every word of a gap is now tried, lowest first. A word inside a gap must also read like a routine laid down beside code: two or more instructions (or a lone `JMP @#f`) that run into known code, or end exactly where known code or another such routine begins, with no `RTS` through a register other than PC, no PC as a plain source and nothing that traps. Without that, tables decode as code (powers of two are `RTS R0`, `BR`, `BNE`...): tried on its own, the wider scan took 27 pieces of data as code. No run has reached the three; they're lifted so that one would. The same audit of the 6502's ROM found nothing.
- **Two data words read as code inside real instructions** (D152 and D182, the operand words of the `MOV`s at D150 and D180). They were guessed from data words holding those values before the jump table at D146 was sized, and the overlap then cut that table short (its other targets were still found, as gaps). A guessed entry that turns out to lie inside an instruction the code's own flow reaches is now dropped, and the analysis runs again: the table has its four targets, and no instruction overlaps another anywhere.
- After both: 27,947 instructions in 805 functions; 0 seeds needed by the five reference runs; both differential tests 0 mismatches; the native run identical to MAME's cores frame for frame on all five.
- **Controllers were ignored while `apb`'s window wasn't the active one** (SDL's default). Started from a terminal on Windows, the focus can stay there; controllers now count either way. `apb` also prints each controller it connects to (or can't open), and `qilin_input_tests` now drives a hot-plugged virtual gamepad (A, Back, the right trigger, the left stick) through the default bindings.
- **With vsync, a queue of old frames could build up.** The game makes 60.1 frames a second and a 60 Hz display takes 60.0, so the swapchain filled until each frame shown was about two frames old: input lag. The newest frame is now shown at each refresh (mailbox), or, matched to the display, the queue holds one at most.
- **The paused menu ran unpaced with a present mode that doesn't wait** (mailbox, or vsync off): it now waits a frame's time unless the display paces it.
- **The black borders around the picture were cleared transparent** (alpha 0). They're opaque now, so a compositor that honours a window's alpha can't show through them.

## [0.16.0] - 2026-11-19
The whole game, natively, the same as MAME's cores frame for frame: both CPUs' lifted code on the board model, the video, the sound and the speech, and `apb`, the game in a window with a settings menu for any wheel, pedal, gamepad or spinner and for the display. Attract mode, a credited game, self-test and random games of up to 60,000 frames give the same picture on every frame as MAME's own T-11 and 6502 cores (`--frame-hashes`), on x86-64 and on ARM64. Rev 7 now needs no seeds: the analysis alone finds everything the game runs. Checked against MAME 0.264 itself: the same pictures, and the same sound (correlation 0.9985, every band that carries it within 0.4 dB).

### Added
- **The settings menu's Display page** (`apb`): full screen (also Alt+Enter or F11, menu open or not), which display the game is on, the picture's size (whole multiples, the sharpest; fit, keeping its shape; or filling the window), smooth or sharp scaling at sizes that aren't whole multiples, vsync, and the graphics device (from the next start). Saved in `apb.ini`; `apb` opens on the display it was last on, full screen if it was. `--no-vsync` and `--gpu N` override the saved choices for one run. The renderer takes them as `Config::scaling`, `smooth` and `gpu_name`, and `set_scaling` and `set_vsync` change them live; it lists the devices that can run it (`devices()`), and scales smoothly only where the device can blit with a linear filter from the frame's format (`smooth_supported()`). Still blits, no shaders; the black borders are cleared only when there are any. Checked under a virtual X display with a window manager and validation: full screen at 1280 × 800 fills (smooth), fits (smooth) and, at 1280 × 1100, doubles exactly; F11 and the page's checkbox agree.
- **Checked against MAME itself** (0.264, run headless with Lua scripts for the coins and snapshots):
  - *Pictures:* MAME's snapshots and ours are the same pixels, frame for frame, once the start is lined up. Our boot finishes 4 frames sooner. That isn't the board: MAME runs each CPU for up to a frame before switching unless something asks it to synchronise, so at start-up each reply from the sound CPU reaches the main CPU later than on the real board; ours switch every 64 cycles. Run with MAME-sized slices (`qilin_refrun --quantum 100000000`), the reference run reads the sound CPU's first reply within 2,000 cycles of MAME.
  - *Sound:* a coined-up game recorded in both (MAME at 48 kHz, ours at the chips' 55,930 Hz, resampled and aligned): correlation 0.9985 on both channels, and the same level within 0.4 dB in every band between 50 Hz and 2 kHz, where the sound is. The one visible difference, the first tenth of a second of the coin sound peaking higher in ours, depends on where the chips' free-running counters are when the sound starts: coining up one frame later in our own run gives MAME's peak.
- **Checked on ARM64.** Cross-built with GCC 14 for the Raspberry Pi 4's Cortex-A72 (`-mcpu=cortex-a72`) and run under qemu: the unit tests pass, and a credited game's 20,000 frames are identical to x86-64's (`--frame-hashes`). The compilers emit about as many instructions for the lifted code on both (ARM64: 0.88 times x86-64's for the T-11, 1.07 times for the 6502), so a Pi 4 should need roughly 125 million instructions a second for the two CPUs, around a tenth of one core, plus the video and sound. That's an estimate: `qilin_run` on a Pi gives the real figure.
- **`qilin_run --io-trace FILE`**: every access the 6502 makes to its chips and latches, with the main-CPU cycle it happened on, for comparing with a MAME Lua tap.
- **`apb`'s display tests**: settings for the display survive a save and load (`qilin_input_tests`).
- **Frame-for-frame agreement with MAME's cores, and the tools to check it.** `--frame-hashes FILE` for `qilin_run` and `qilin_refrun` writes a hash of every frame's colours, one line a frame; the two files of a run are identical. The controls are scripted in one place (`tools/common/script.hpp`, shared by `qilin_run`, `qilin_refrun` and `qilin_handoff`) and change on the exact cycle of each vblank (`Machine::on_vblank`), so both runs see them change at the same moment.
- **`apb` built and run.** Against SDL3 3.4.20, fetched by CMake (`QILIN_FETCH_SDL3`), on Linux with the X11, Wayland and audio development packages SDL lists; run in a virtual X display through Mesa's software Vulkan, it shows attract mode in its window and saves the EEPROM on exit. Its controls now change at the start of each vblank (`Machine::on_vblank`), as the tools' do.
- **The settings menu, and any wheel, pedal, gamepad or spinner** (`apb`). F1 or Escape (Start or Guide on a gamepad) pauses the game under a menu (Dear ImGui, MIT, vendored at v1.93.0 in `third_party/imgui` with its SDL3 and Vulkan backends; the renderer draws it in a dynamic-rendering pass over the window's image, after the game's picture). Its first page is the controls:
  - every connected controller, read as a raw SDL joystick (a wheel and its pedals are often two devices, and few are known to SDL's gamepad mappings), with its type, axes, buttons and whether it has force feedback;
  - steering by keys and gamepad (always), a wheel, or a mouse or spinner. A wheel is found by turning it; its rotation is set to match its driver (presets, or measured by turning it one full turn); its sensitivity is in dial counts per turn; wheels that stop at a lock can keep the dial turning while held there (`controls.hpp`); it can be reversed. The bound wheel gets no centring spring and an adjustable friction (or damper) through SDL's haptics, so it feels like the cabinet's free wheel;
  - a pedal, found and calibrated by pressing it to the floor and letting go (resting at either end of its axis);
  - any button, key, hat or axis added to each of the cabinet's buttons and coins;
  - meters for the wheel, the dial counts and the gas.
  Settings are saved to `apb.ini` next to the EEPROM when the menu closes and on exit. The Game page has the self-test switch and Quit.
- **`qilin_input_tests`**: the controls on SDL's virtual joysticks, a wheel and pedals as two devices: finding the wheel, a quarter turn moving the dial 40 counts, holding at the lock, finding and calibrating a reversed pedal, binding a wheel button, the settings file, and the controls resting while the menu is open.
- **`controls.hpp`** (`recomp/runtime/app/`), the arithmetic for playing with what the player has, unit-tested: a PC wheel's absolute angle turned into APB's free-spinning dial (the distance it moves each frame, in counts per turn of the wheel), with an edge near each lock where holding the wheel keeps the dial turning, for wheels that stop; a rate for sticks and keys; pedals calibrated by their released and floored readings, reversed ones included.
- **The System 2 board as both CPUs see it** (`recomp/runtime/system2_machine.*`, library `qilin_board`), after MAME's `atarisy2.cpp`: the main map (RAM, palette, ROM banks, the Slapstic video view, CP0-CP3 latched from the interrupt enable, which applies at the next synchronisation as MAME's `synchronize` does, IN0 with the two latches' pending bits, the watchdog, the ADC) and the sound map with all of MAME's mirrors (RAM, EEPROM, two POKEYs, the YM2151's busy flag, the TMS5220, IN1, the LETA dial, the latches, the IRQ acknowledge). Events in main-CPU cycles, all whole numbers: the 32V interrupt every 64 lines, VBLANK at line 384 (166,400 cycles a frame), the 244 Hz sound IRQ (40,960 cycles, never while the 6502 is held in reset) and the watchdog (1,048,576). Unit-tested against MAME's definitions.
- **`qilin_refrun`** (`tools/refrun/`, needs your ROMs): the game on MAME's own T-11 and 6502 cores and that board, in 64-cycle slices, with every executed address recorded; coins, buttons, the pedal and the steering dial can be scripted. On rev 7 it runs the power-on tests, releases the sound CPU, completes the start-up handshake and runs attract mode and a credited game with no watchdog reset, two minutes of game time in 7 s. It compares what ran with both analyses and turns what the analysis missed into seeds (`--seeds-out`), re-analysing until everything executed is covered: 36 seeds over three runs, all of them entries reached only through RAM handler tables, pointers in data records or far-call trampolines. Every 6502 address executed was already found.
- **`--seeds FILE`** for `qilin cfg` and `qilin lift`.
- **The game's scheduler** (`recomp/runtime/game/`): both CPUs' lifted code on the board model. The T-11 leads; at each of its service points the machine's clock advances, the 6502's lifted code catches up in a slice it ends by yielding, the board's events run, and a pending T-11 interrupt is taken, its handler running natively, as MAME takes them at the start of a timeslice. Interrupt sequences make MAME's bus accesses and charge its cycles (T-11 114, 6502 7, 6502 reset 8). Stops (frame count, watchdog, unlifted code) end the run with the reason.
- **`qilin_run`** (`tools/run/`, needs your ROMs and both lifts): runs the game natively with the reference run's scripted inputs. On rev 7, attract mode and a credited game each run 20,000 frames (5.5 minutes of game time) in under 6 s, about 60 times real time on one core, with no unlifted code and no watchdog reset: 112,918 sound commands, 155,215 main-CPU interrupts. `--log` and `qilin_refrun --log` write the latch, IRQ and reset traffic of a run for comparing the two.
- **Video, the CPU reference** (`recomp/runtime/system2_video.*`, library `qilin_video`), after MAME's `atarisy2_v.cpp` and `atarimo.cpp`: the graphics ROMs decoded with MAME's layouts; the 128 × 64 playfield with its tile banks and priority categories, scrolled as MAME scrolls it (X from the register, Y less the scanline it was written on or loaded at line 0); the linked motion-object list from entry 0 with neighbor placement and MAME's wrap against its 640 × 416 bitmap; MAME's merge (a motion object loses only to playfield pens 8-15 of a high-priority category); the alphanumerics on top; the palette; the cabinet's ROT270. Frames are drawn in bands, as MAME's partial updates draw them: the machine tells its video sink before a changed scroll register or a write to motion object 0's link, and at the start of vblank. APB rebuilds its sprite list mid-frame, so this is needed for the player's car to appear where it is. Unit-tested on synthetic ROMs.
- **The renderer shows frames in a window** (`gfx.hpp`): `write_back_buffer` replaces the back buffer with CPU pixels (a staging copy), and with a surface from the windowing library (`Config::create_surface` and its instance extensions) each `present` also blits the frame to the window's swapchain, scaled by the largest whole number that fits (below 1×, the largest fit, filtered), centred on black. ### Fixed
- **A jump table proven by value ranges could lose to a guess.** A code pointer guessed from a data word (D5D4, decoded as `NEG 1003(R0)`) had taken the third word of a `CMP @#a,@#b` that a proven table jumps to, so the table's first target (D5D0) looked like it ran into another instruction, and the table was dropped: four of its targets needed seeds. - **Settings menu and controls, found in review before anyone played with them:**

  - ImGui's SDL3 backend wasn't shut down if its Vulkan backend never started.
- **Interrupts and slices land on the same instruction as on MAME's cores.**
  - Lifted code checks its slice before every instruction (`--service-interval 0`, now the default for both CPUs), as MAME's cores run whole instructions until the slice is used up. The old way (at loop back edges and after straight runs of 128 or 64 cycles) let a slice overrun by up to that, so events and interrupts landed late. It costs about half the speed: a credited game runs at 34 times real time on a desktop core instead of 68 (`--service-interval 128` gives the old way).
  - The board sees MAME's local time at every access to its chips, latches and video: the slice's start plus the cycles the instruction has charged (T-11: all of an instruction's, before its accesses; 6502: the bus cycles before this one). It used to see the slice's start, so a scroll write drew its band at the wrong scanline and the speech chip's /READY came at the wrong cycle. The reference run had the same error (the instruction's start): fixed there too.
  - **T-11:** an interrupt taken at a slice's start runs the handler's first instruction in that slice, as MAME's step does; after RTI, RTT or MTPS it is taken in the same step, without the board getting its turn first (`check_interrupts`). A handler that returns having used up its slice gives the board its turn at once. Events due at power-on run before the first instruction. WAIT idles a slice at a time, not to the next event, so a line the sound CPU raises is seen at the same slice boundary.
  - **6502:** MAME decides on an interrupt at the end of each instruction, from the lines it sampled during it and the I flag as it was before CLI, PLP or SEI changed it (after RTI, as RTI left it). The native scheduler did it at slice starts on the current flag. It now does it MAME's way (the lifted code tells the board around CLI, PLP, SEI and RTI), and the sequence picks its vector as it runs, so an NMI that arrives in time wins over the IRQ that started it.
- **Guessed entries are held to what code looks like** (pointer immediates, code pointers in data, gaps). Data had been lifted as code: a menu record in bank 14 (577A), text decoded as `CMP R0,-(R0)` (575A), the bit table's neighbours, and `BIC R5,PC` "computed jumps" at 4F14/b15 and 5AB8/b14. A guessed entry is now rejected if it starts with a branch or a JMP other than `JMP @#f` into the fixed ROM (a stub), if its new code has four instructions in a row whose opcode words are printable ASCII (the game's own code never has more than two), if it returns with words still pushed or pops below its return address (a pushed pointer, `MOV #a,-(SP)`, may pop what its pusher left: a continuation), or if it reaches RTI (a pointer immediate may: a handler) or a JMP/JSR to `-(Rn)`. A pointer immediate to a bank entry table's slot is the address of a function pointer, not code (`MOV #4022,-(SP)` passes slot 4022 of bank 15's table), and pointer immediates are seeded only once the bank tables are known. Every location the reference runs executed is still covered.
- **The T-11 takes a pending interrupt at once after MTPS, RTI and RTT**, as MAME's core does (it checks its lines after those instructions, not only at the start of the next timeslice). Lifted code checked after MTPS only when its cycles had run out, and not at all after an RTI that didn't return into the scheduler (APB's task switches). So an interrupt the game had just unmasked was taken later and deeper in the code: in one random game (`--monkey 2`, 3 minutes in) a task's stack, which grows down from 0x0100 towards the vectors, went 14 bytes deeper than on MAME's cores, overwrote a vector, and the game stopped. `qilin_handoff` found it: from the native state a frame earlier MAME's cores stayed 8 bytes clear. The board now has `interrupt_due()`, and lifted code services at once when it's true after those instructions. With it, the native run gets through attract mode, a credited game, 16 random games of 60,000 frames and 11 self-test sessions with no stop.
- **A T-11 interrupt handler always runs an instruction before the next interrupt is taken**, as MAME's T-11 does (its execute loop is a do-while). Natively a handler could reach a service point at its entry, before any instruction, and be interrupted again there.
- **A sound command could lose its NMI.** The scheduler looked at the latch's line only between 6502 slices, so a command read and the next one written in between left it high both times and no edge was seen; the 6502 then waited forever for a byte. The machine now counts the line's rising edges (a command written to an empty latch, as MAME's latch asserts it), and every one is taken.
- **The T-11 lifter left `JMP @X(Rn)` tables through dispatch**, where their targets have no entry; they now go to their targets' labels, as `ADD X(Rn),PC` tables do. Both kinds of table jump also service the board when cycles run out, since a loop can run through one.
- **Lifted T-11 code can be re-entered wherever it may have been interrupted:** at service points and table targets as well as function starts and return sites. APB's interrupt handler switches tasks, returning to code interrupted earlier, elsewhere.
- **`JMP @X(Rn)` jump tables were sized but never applied**: exploration only used resolved tables for `ADD X(Rn),PC`. The reference run found the one at `8820` by executing it.
- **Value ranges narrow on `BIT #mask,Rn`** where the mask is a run of high bits (`BIT #177740,R1 / BEQ`: R1 < 32), which proves that table.
- **An entry in a window is explored with its own bank known.** Seeds and pointer entries in banked code used to advance one instruction per analysis round.
- **Pointer immediates into the code's own window** (`MOV #4D34,52A(R0)` in bank 12) are entries in that bank. Guessed pointers must now look like ordinary code: no traps or `RTT` and no repeated identical branch, which rejects two data tables in bank 2 that had been decoded as code.

- **Function discovery from the code's own structure:** the register-save helpers (found structurally: a `JSR Rn,@#H` target that continues its caller with `JSR PC,@(SP)+`) and the 208 prologues that call them; the entry table each code bank starts with (98 entries); pointer immediates (`MOV #addr`), each validated by decoding before it counts; interrupt vectors installed by immediate stores.
- **Bank windows inferred from the ROM:** each bank's absolute references to itself say which window it runs in. Banks 0-2, 4-6, 8, 10 and 12-15 run in window 0; the rest are data.
- **Heuristic jump tables** where the index comes from memory: entries read until the first implausible one, marked as such; the lifted code will check every index at run time.
- **Unit tests for the analysis** on synthetic ROMs: a loop-indexed table proven to its exact size, prologue seeding, bank-window inference, and an unknown-bank entry reported.

### Fixed
- A table proven before a loop's back edge was explored kept its first, too-small size. Tables are now re-proved every round.


## [0.12.0] - 2026-11-18
The project is rebuilt to GBTGhoulies-Qilincomp's requirements and layout. The T-11 decoder is complete and verified against MAME on every opcode word. The earlier translator is retired; `docs/recompiler-core.md` says why.

### Added
- **`qilin`**, the recompiler CLI: `qilin verify <rom-dir>` checks all 36 rev 7 files (size and SHA-1, in C++ instead of a CMake script); `qilin insns <rom-dir>` lists T-11 code at CPU addresses under chosen banks, in MAME's syntax with cycle counts.
- **The ROM set loader** (`recomp/src/romset.*`): MAME's complete `apb` layout for all five regions (byte lanes, `ROM_CONTINUE` pieces, the inverted sprite region, zero fill), with every problem named.
- **A full T-11 decoder** (`recomp/src/t11_decoder.*`): every instruction the chip executes, EIS and `MARK` decoded as traps, MAME's cycle counts, MAME-format disassembly.
- **MAME's T-11 core as the reference CPU** (`third_party/mame-t11`, BSD-3-Clause): MAME's opcode files unmodified, behind a bus interface that traces every cycle and counts cycles as MAME does.
- **`qilin_t11_decoder_check`** (CI): disassembly, length, cycles and traps of all 65,536 opcode words against MAME's disassembler and core. All agree.
- **Board model tests against MAME's definitions:** the bank table, the palette formula on every value, and the Slapstic 110 on random bus traffic against a transcription of MAME's state machine (0 mismatches).
- **The System 2 memory map** as code (`sys2::area`), from MAME's `main_map`, mirrors included.
- **Design documents:** `docs/roadmap-and-design-targets.md` (the Ghoulies requirements as they apply to System 2), `docs/system2.md` (the board, from MAME), `docs/recompiler-core.md`, `docs/naming.md`.

### Changed
- **Layout and naming follow GBTGhoulies-Qilincomp:** `recomp/src`, `recomp/runtime`, `recomp/tests`, `tools/check`, `third_party`; `qilin` and `QILIN_*` in place of `apb-t11-aot` and `APB_*`.
- **The renderer is GBTGhoulies-Qilincomp's** Vulkan 1.3 renderer (dynamic rendering, synchronization2, volk loading, validation-checked in CI), without depth and stencil, which 2D System 2 video doesn't use.
- **Vulkan headers and volk are vendored**, so a clone builds offline; configure no longer downloads anything.
- **CI** runs on every push, with the same six configurations as GBTGhoulies-Qilincomp.

### Removed
- **The PC-and-bank translator** (`apb-t11-aot`), its ROM and jump-table map files, and the CMake ROM verifier. Code generation is being rebuilt around physical ROM addresses (`docs/roadmap-and-design-targets.md`).
